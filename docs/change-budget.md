# 变更预算（Change Budget）

> **目的**：为每次开发任务划清"能改什么、不能改什么"，标注冻结层，**防止顺手重构**。
> **与影响分析的关系**：`module-dependencies.md` 回答"改了会影响谁"，本文档回答"哪些根本不能改 / 哪些要审批才能改"。

---

## 1. 三层变更分类

| 层级 | 含义 | 改动规则 |
|---|---|---|
| 🔒 **冻结层** | 业务契约 + 已定架构决策，是系统的"宪法" | **禁止顺手改**。要改必须走「决策变更流程」（见 §4） |
| 🟡 **受控层** | 允许改，但有连带影响（契约/接口/状态机） | 改前先声明"怎么变、为何变"，并同步更新测试 + 文档 |
| 🟢 **自由层** | 正常开发的实现细节 | 可自由改，遵循影响分析即可 |

---

## 2. 冻结层清单（🔒 绝对禁止顺手改）

### 2.1 业务契约（定义在 `business-rules.md`）

| 冻结项 | 为什么冻结 | 想改的正确路径 |
|---|---|---|
| 角色枚举（`admin`/`tech`/`instructor`） | 权限矩阵的根基，改了所有鉴权失效 | 走决策变更：新增决策文档 + 全量回归 |
| 权限矩阵（谁能否做什么） | 安全边界，业务规则 | 同上 |
| 需求状态机语义（8 个状态的含义） | 业务核心流程 | 同上 |
| 状态机流转规则（`allowed_transitions`） | 非法流转要拒绝，是防越级的网 | 同上 |
| 防幻觉铁律（LLM 只产候选，人工确认） | 系统第一原则 | 同上 |
| 需求来源枚举语义（`training`/`discussion`/`manual`/`reuse`/`internal`） | 需求溯源的基础 | 加枚举值可走受控，改语义走冻结 |

### 2.2 已采纳的架构决策（`decisions/*.md` 里的 8 项）

| 决策 | 核心结论 |
|---|---|
| 01 纯内部工具 | 客户无账号 |
| 02 多用户数据模型 | 从第一天就是多用户 |
| 03 LLM 双源 | 大模型分析 + 小模型去噪 |
| 04 录音流水线 | 不做三方说话人分离，小模型去噪 |
| 05 需求状态机 | 两类调整 + 不可行可重评 |
| 06 防幻觉铁律 | 人工确认落库 |
| 07 答疑 agent | 关键词检索 + 回流 |
| 08 部署路径 | 先内网电脑、后公司服务器 |

**这些决策如果被"顺手推翻"，等于否定之前所有评审。** 要改，必须新开决策文档标记"已变更 + 原因"。

### 2.3 测试（`tests/`）

| 冻结项 | 规则 |
|---|---|
| 现有测试用例 | **禁止删测试来掩盖回归**；禁止改测试断言来"让失败变通过" |

## 3. 受控层清单（🟡 允许改，但需声明 + 同步）

| 受控项 | 改动时必做的事 |
|---|---|
| 接口契约（`schemas.py` 的字段、API 请求/响应形状） | 声明变更 + 同步前端 `api` 调用 + 同步测试 |
| ORM 模型字段（`models.py`） | 声明变更 + 全量回归 + 更新 `module-dependencies.md` 影响面 |
| LLM/ASR 抽象接口（`get_llm`/`get_asr` 签名） | 声明变更 + 同步所有调用方 + 测试 |
| 配置字段（`config.py`） | 声明变更 + 同步 `.env.example` |
| 状态机实现（`state_machine.py`） | 声明变更 + 同步 `test_state_machine.py` + 更新 `business-rules.md` |

---

## 4. 决策变更流程（要动冻结层时的正确姿势）

1. **停下来**，不要顺手改。
2. **写变更说明**：动哪个决策/契约、为什么过时了、新结论是什么、备选方案为何被否。
3. **更新文档**：
   - 在对应 `decisions/NN-*.md` 顶部加"⚠️ 已变更"标记 + 指向新决策；
   - 或新增 `decisions/09-*.md` 记录新决策；
   - 同步 `business-rules.md`（若涉及业务契约）。
4. **再改代码**，并跑全量回归。
5. **提交**，commit message 里注明"变更决策：X → Y"。

---

## 5. 顺手重构判定（红线）

做任务时，遇到"顺便改一下更好"的冲动，先问自己：

1. **这个改动服务于当前任务的明确目标吗？** 不服务 → 是顺手重构，停。
2. **这个改动在任务开始前声明的预算范围内吗？** 不在 → 是顺手重构，停。
3. **改的是冻结层/受控层吗？** 是 → 走 §4 流程，不走"顺手"。
4. **这个改动会被本次的测试覆盖吗？** 不会 → 别改，或先补测试再改。

> **铁律：一个任务 = 一份预算。超出预算的改动，无论看起来多好，都必须停下来重新评估，而不是顺手做完。**

---

## 6. 每个任务的"预算声明"模板

开始任何开发任务前，用一句话声明预算（可写在 commit 或任务说明里）：

```
预算：本任务只改 <模块/文件>，目标是 <一句话目标>。
冻结：不触碰 <models.py 枚举 / 状态机 / 权限 / 已定决策 / 现有测试>。
越界：若发现必须改冻结层，停下来走决策变更流程，不顺手改。
```

## 7. 与现有文档的关系

| 文档 | 回答的问题 | 本文档的分工 |
|---|---|---|
| `business-rules.md` | 业务规则是什么 | 本文档把它标为"冻结层" |
| `decisions/*.md` | 为什么这么设计 | 本文档规定"改了要走的流程" |
| `module-dependencies.md` | 改了影响谁 | 本文档规定"哪些不能改" |
| `AGENTS.md` | 怎么上手 | 本文档是它的强制补充 |
