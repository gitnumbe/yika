# 业务规则（Business Rules）

> 本文件是系统**业务层面必须遵守的规则**，与实现解耦。代码实现了这些规则，但规则本身在这里定义。改代码时若与这些规则冲突，先回来看这里。

## 1. 角色与权限

系统是**纯内部工具**，三类角色，客户无账号。

| 角色 | 枚举值 | 定位 |
|---|---|---|
| 管理员 | `admin` | 管用户、管系统配置（模型/ASR 参数）、备份导出 |
| 技术人员 | `tech` | 答疑、布置学习任务、需求可行性评审、开发 |
| 讲师 | `instructor` | 学习提问、做学习任务、录音、记笔记、参与需求探索 |

### 权限矩阵（核心操作）

| 操作 | 讲师 | 技术 | 管理员 |
|---|---|---|---|
| 录音 / 看笔记 | ✅ | ✅ | ✅ |
| 提问 / 答疑 | ✅ 提问 | ✅ 答疑 | ✅ |
| 学习任务 | ✅ 做任务 | ✅ 布置/批改 | ✅ |
| 需求录入 | ✅ | ✅ | ✅ |
| 需求流转（评审） | ❌（只看结果） | ✅ | ✅ |
| 开发任务 | ❌ | ✅ | ✅ |
| 知识库写入 | ❌（只读） | ✅ | ✅ |
| 备份导出 | ❌ | ❌ | ✅ |
| 系统配置 | ❌ | ❌ | ✅ |

**实现约束**：权限必须在**后端**用 `require_role` 强制，前端只做 UI 隐藏，不作为安全边界。

## 2. 需求状态机

状态与流转（`backend/app/state_machine.py`）：

```
draft → pending_review → feasible → in_dev → delivered
              ↘ info_needed ──→ pending_review（信息待补充，返讲师）
              ↘ plan_needed ──→ pending_review（方案待调整，返技术）
              ↘ infeasible ───→ pending_review（不可行，可重新评估）
```

状态语义：

| 状态 | 含义 | 下一步归谁 |
|---|---|---|
| `draft` | 草稿（刚录入/刚提炼确认） | 提交评审 |
| `pending_review` | 待评审 | 技术人员评审 |
| `feasible` | 可行（待开发） | 技术开发 |
| `in_dev` | 开发中 | 技术 |
| `delivered` | 已交付 | （终态） |
| `info_needed` | 信息待补充（需求没说清/缺信息） | **讲师**补充后重提 |
| `plan_needed` | 方案待调整（需求合理但方案要改） | **技术**改方案后重提 |
| `infeasible` | 不可行（附原因，归档不删） | 可「重新评估」回待评审 |

**关键规则**：
- 非法流转必须被拒绝（抛 `ValueError` → 400）。
- `infeasible` 必须带原因，且**归档不删除**——技术边界变化后可重新评估。

## 3. 需求来源（source 枚举）

每条需求必带来源，用于溯源"这条需求从哪冒出来的"：

| 枚举值 | 含义 |
|---|---|
| `training` | 培训记录 |
| `discussion` | 三方探讨 |
| `manual` | 手动输入 |
| `reuse` | 过往需求复用 |
| `internal` | 内部/产品化立项 |

来源是**字段**，不是独立入口；未来加来源只加枚举值。

## 4. 录音场景标签

录音时必选场景，决定笔记去向和后续动作：

| 场景 | 枚举/取值 | 笔记归档 | 后续动作 |
|---|---|---|---|
| 内部沟通（答疑/学习） | `internal` | 知识库/学习区 | 沉淀为答疑记录 |
| 客户需求探索 | `discussion` | 项目空间·需求探索 | 触发需求提炼 |

## 5. 防幻觉铁律（核心原则）

> **LLM 只产「候选/建议」，任何落库决策由人确认。**

- 需求提炼产出只进「候选区」，人工编辑（改/合并/拆分/删/补来源）确认后才成 `draft`。
- 可行性初筛 agent 只给技术参考，最终结论技术拍板。
- LLM 产出永远**不直接写需求库**，避免编造需求污染评审流程。

这条铁律贯穿所有 agent，是系统设计的**第一原则**。

## 6. 业务闭环

```
讲师学习(AI知识) → 讲师培训客户 → 三方沟通挖需求 → 总结需求
  → 技术逐条评审(排不可行) → 技术开发 → 交付 → 客户验收反馈
```

- 培训记录、三方探讨、手动输入都会进需求提炼（不是只有"客户需求场景"才提炼）。
- 交付后要有验收反馈，反馈可转新需求（闭环，不是断头路）。
