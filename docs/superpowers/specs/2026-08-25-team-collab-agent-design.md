# 组内队员协作 Agent —— 设计文档

- **日期**：2026-08-25
- **状态**：已评审（工程评审 + CEO 评审通过，见 §8 决策记录）
- **定位**：纯内部工具，服务「技术人员 + 讲师」两类角色，无客户账号

---

## 1. 背景与目标

团队分为**技术人员**和**讲师**两类角色。对于一个客户项目，业务流程如下：

```
讲师学习 AI 知识（问技术/自学/做实践任务）
  → 讲师给客户培训（AI 通识、过往案例、要为客户设计的 agent 系统）
  → 讲师 + 技术人员 + 客户 三方沟通，挖掘潜在需求
  → 总结需求清单
  → 技术人员逐条评审落地方案，排除无法实现的需求
  → 技术人员开发交付
```

**核心痛点**（决定系统骨架）：
1. 讲师缺 AI 知识，频繁依赖技术人员答疑
2. 三方沟通难沉淀成结构化需求
3. 需求可行性全靠技术人员脑内判断，无沉淀

**目标**：一个桌面应用 + 内网中央服务，把上述流程数字化，并用 AI agent 消除三个摩擦点。

## 3. 状态机

### 3.1 项目状态机

```
筹备/学习 → 培训中 → 需求探索 → 需求评审 → 开发中 → 已交付
```

### 3.2 需求状态机（核心）

```
草稿 → 待评审 → 可行(待开发) → 开发中 → 已交付
             ↘ 需调整 ──→ 信息待补充(→讲师)  → 重新提交评审
             │        └→ 方案待调整(→技术)  → 重新提交评审
             ↘ 不可行(归档，附原因) ── 可重新评估 → 回到待评审
```

**关键规则**：
- 每条需求必带**来源引用**（哪次沟通/录音/笔记），可点回原文。
- **信息待补充**：需求没说清、缺信息，返讲师补充后重新提交。
- **方案待调整**：需求合理但方案要改，返技术人员改方案后重新评审。
- **不可行**：归档不删除，附原因；技术边界变化后可「重新评估」回到待评审。

## 4. 录音数据流与 Agent

### 4.1 录音 → 转写 → 笔记 → 需求

```
【采集】桌面悬浮球/全局快捷键，任意时刻启动（可暂停/续录/结束）
   → 录音时选【场景标签】+ 勾选在场人
【转写】后端异步任务：Qwen3-ASR-1.7B 中文转写（带时间戳·决策 09）
   → 产出转写文本
【去噪】小模型初筛废话（寒暄/重复/口水话），保留干货句
【整理】大模型 把干货句 → 结构化笔记
【提炼】大模型从笔记 → 候选需求 → 人工编辑确认 → 需求库(草稿)
```

**录音场景标签**（决定笔记去向与后续动作）：

| 场景 | 笔记归档到 | 后续动作 |
|---|---|---|
| 🎓 内部沟通（答疑/学习） | 知识库/学习区 | 沉淀为答疑记录 |
| 🤝 客户需求探索 | 项目空间·需求探索 | 触发需求提炼 |

### 4.2 说话人处理（R2 决策）

**不做三方说话人分离**（讲师/技术/客户）。主链路：小模型去噪 + 大模型分析。

- **内部沟通场景**：纯去噪 + 分析，不区分人。
- **客户需求场景**：叠加**二分类（内部人 vs 客户）**，用于标记"客户潜在需求线索" vs "内部结论/待办"。二分类准确率远高于三方分离。

### 4.3 结构化笔记模板

大模型固定输出四块（结构化约束，防自由发挥）：

| 区块 | 内容 |
|---|---|
| 一句话摘要 | 这次沟通说了什么 |
| 分段要点 | 按话题分节 |
| 决策 | 达成的一致结论 |
| 待办/疑问 | 谁做什么、还有什么没定 |

### 4.4 防幻觉铁律

**LLM 只产"候选/建议"，任何落库决策由人确认。** 需求提炼产出候选需求，每条带来源引用，进入「需求编辑区」（可改/合并/拆分/删/补来源），人工确认后才成草稿进状态机。

## 5. Agent 清单与行为

贯穿所有 agent 的铁律：**LLM 只产建议，落库决策人确认；输出带引用溯源。**

| Agent | 输入 → 输出 | 边界 |
|---|---|---|
| **答疑 agent** | 讲师提问 → 先检索知识库；有答直接回（带引用）；无答/低置信转「待答疑」队列 @技术人员；技术人员作答后问答对回流知识库 | 转人带上下文；问答回流形成闭环 |
| **需求提炼 agent** | 客户场景笔记 → 候选需求（标题/描述/来源引用） | 只进候选区，不直接改需求库 |
| **可行性初筛 agent** | 待评审需求 → 预判建议（可落地/需调整/不可实现 + 理由 + 引用技术边界） | 只给技术人员参考，最终结论技术人员拍板 |
| **学习推荐 agent** | 讲师答疑记录暴露的盲区 → 学习路径建议 | 技术人员布置任务时可参考 |
| **会议纪要 agent** | = 录音链路里的笔记整理环节 | 见 §4 |

**Agent 数据流串接**：

```
录音(客户需求) → 转写 → 去噪 → 笔记整理 → 需求提炼agent → 候选需求
   → 人工编辑确认 → 需求库(草稿) → 可行性初筛agent(预判) → 技术人员评审
录音(内部) → 笔记 → 知识库 ←—— 答疑agent(检索+回流)
```

## 6. 数据模型（核心实体）

- **用户 User**：id、用户名、密码、角色（admin/tech/instructor）
- **客户 Customer**：id、名称、行业、联系人
- **项目 Project**：id、名称、关联客户、状态、成员
- **笔记 Note**：id、关联项目、场景标签、转写原文、结构化笔记四块、时间戳
- **需求 Requirement**：id、标题、描述、**来源(source)**、来源引用、关联项目/客户、提出人、状态、评审结论、不可行原因、优先级
- **学习任务 LearningTask**：id、布置人、执行人、内容、状态、批改
- **答疑记录 QA**：id、问题、回答、关联知识库条目、状态
- **知识条目 Knowledge**：id、标题、内容、来源（手动导入/答疑回流）

**需求来源 source 枚举**：`培训记录 / 三方探讨 / 手动输入 / 需求复用 / 内部立项`（可扩展）

## 7. 技术栈与部署

| 层 | 选型 |
|---|---|
| 后端 | Python 3.10 + FastAPI |
| 数据库 | SQLite 起步 → Postgres |
| 桌面壳 | Electron + React + TypeScript |
| LLM | 抽象层，默认内网大模型（OpenAI 兼容，**实例见 Obsidian `yika/开发文档` §4.0 基线表**，当前 `deepseek-v4-flash-vision-exp`） |
| STT | 抽象层，默认 Qwen3-ASR-1.7B（本地自建·决策 09），`POST /v1/transcribe` |
| TTS | 抽象层，默认 dots.tts-mf（本地自建·决策 09），`POST /v1/speak`，笔记/答疑朗读（v2.0 新增） |
| 去噪 | 本机 Ollama 小模型（当前 `qwen3:4b-instruct`，句子级二分类），MVP 可先用规则/关键词过渡 |

**部署路径**：
- 初期：后端跑在**内网普通电脑**，本机多开（多账号多角色登录）模拟协作，不投入生产
- 成熟后：迁公司服务器，换 IP 即可，代码零改动
- **数据模型从一开始就是多用户的**（每条数据挂 user_id、按角色分权限）

**长文本（R4 决策）**：MVP 按单次录音独立处理，单次约 1.2万-1.8万 token，不超窗。不预建 RAG/切分；将来超窗再加（文本切分器 / Map-Reduce 摘要 / 向量检索 / token 预算管理）。

## 9. 功能清单与分阶段范围

### MVP（第一阶段：验证核心闭环）

- 账号登录（F1，最小用户名密码）
- 客户/项目档案（F6）
- 需求状态机（含信息待补充/方案待调整/不可行可重新评估）
- 录音 → 转写 → 去噪 → 笔记 → 需求提炼（完整数据流）
- 答疑 agent + 知识库（含手动导入 F4）
- 数据备份/导出

### 第二阶段（补齐协作体验）

- 通知/提醒（F2）
- 全库搜索（F3）
- 可行性初筛 agent
- 培训模块（F5：课件/大纲/培训记录）
- 交付闭环（P4）

### 第三阶段（锦上添花）

- 学习推荐 agent
- 说话人标签人工修正兜底
- RAG / 长文本切分（R4 兜底项）
