# 决策 02：数据模型从第一天就是多用户

**状态**：已采纳
**日期**：2026-08-25

## 背景

初期部署在"内网一台普通电脑"上，且用户本人打算**本机多开**（多账号多角色登录）来模拟协作，成熟后再迁公司服务器让真实多人使用。

问题：数据模型要不要先做成"单用户"（简单），等迁移时再改？

## 决策

**从第一天就是多用户。** 所有核心实体挂 `author_id` / `user_id` 外键，权限按角色分。即使是本机多开模拟，也用真实的多账号。

## 为什么这么设计

1. **数据结构是最难迁移的东西**。代码可以重写，但"单用户改多用户"意味着所有表加外键、所有查询加过滤、所有接口改鉴权——这是灾难性的重构，而非简单的增量。
2. **本机多开恰好验证多用户**。既然最终要多人协作，本机多开（多账号多角色）正好用最便宜的方式验证了多用户架构的正确性。
3. **迁移零成本**。数据模型是多用户，从内网电脑迁到公司服务器只是换 IP，代码零改动。

## 备选方案（为何没选）

- **先单用户，后迁移**：迁移时几乎重写数据层和鉴权层，得不偿失。这正是"数据结构不设临时版"的反面教材。

## 核心原则

**数据结构不做"临时版"。** 一开始就按最终形态设计，哪怕初期只有一个人用。

## 关联代码

- `backend/app/models.py` — `Requirement.author_id`、`Note.author_id`、`QA.author_id`、`Recording.author_id`、`LearningTask.assigner_id/assignee_id`
- `backend/app/auth.py` — `get_current_user` + `require_role` 鉴权
- `backend/app/schemas.py` — 所有接口都基于登录用户身份
