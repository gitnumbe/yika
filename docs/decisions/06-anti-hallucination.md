# 决策 06：防幻觉铁律（LLM 只产候选，人工确认）

**状态**：已采纳（第一原则）
**日期**：2026-08-25

## 背景

系统的核心价值之一，是"把沟通内容自动提炼成需求"。但 LLM 会**幻觉**——编造需求、曲解客户意图、无中生有。

如果 LLM 的产出直接写进需求库，污染的会是一条链路：错误需求 → 错误评审 → 错误开发 → 交付错的东西。

## 决策

> **LLM 只产「候选/建议」，任何落库决策由人确认。**（防幻觉铁律）

具体落地：

1. **需求提炼**：LLM 产出候选需求，每条带「来源引用」，进入「需求编辑区」。人工可改/合并/拆分/删/补来源，点「确认」后才变成正式 `draft` 进状态机。
2. **可行性初筛 agent**：只给技术人员预判参考（可落地/需调整/不可实现 + 理由），最终结论技术拍板，初筛不改状态。
3. **LLM 产出永远不直接写需求库。**

## 为什么这么设计

1. **需求库是系统的核心资产**，一旦被幻觉污染，会传导到评审、开发、交付，代价高昂。
2. **人最擅长判断"这到底是不是客户要的"**，LLM 擅长"从海量文本里抓候选"。两者分工：LLM 提候选（快），人做确认（准）。
3. **带来源引用让确认可验证**——人点一下能跳回原文，判断 LLM 有没有曲解。

## 备选方案（为何没选）

- **LLM 直接落库**：省一步人工，但幻觉风险不可控，需求库会慢慢不可信。
- **纯人工提炼**：准但慢，违背"用 AI 消除摩擦"的初衷。

## 核心原则

**AI 提建议，人做决策；不可信输出不进可信数据。** 这条铁律的优先级高于一切"效率"考量。

## 关联代码

- `backend/app/services/req_extract.py` — 只产出候选（返回 list，不落库）
- `backend/app/routers/notes.py` — `/notes/{id}/extract`（返回候选）与 `/notes/{id}/confirm-requirements`（人工确认后落库）分离
- `backend/app/schemas.py` — `CandidateRequirement` / `ConfirmRequirements`
