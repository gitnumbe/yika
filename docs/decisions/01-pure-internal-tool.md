# 决策 01：纯内部工具（客户无账号）

**状态**：已采纳
**日期**：2026-08-25

## 背景

团队分技术人员和讲师，围绕"为客户设计 agent 系统"开展项目。起初需要决策：客户是否登录系统参与协作？

三个选项：
- A. 纯内部工具（客户不进来）
- B. 客户轻参与（只读培训材料、提需求、看结果）
- C. 客户全参与（客户是一等公民，全程在线协作）

## 决策

**选 A：纯内部工具。** 客户无账号，系统只服务讲师 + 技术人员。三方沟通（讲师/技术/客户）在线下或微信进行，内部人把结论录进系统。

## 为什么这么设计

1. **客户参与不是当前痛点**。痛点是"讲师缺 AI 知识 + 需求难沉淀 + 可行性靠人脑"，这三条都发生在**内部**，不涉及客户登录。
2. **降低工程量与安全面**。客户进来意味着要做客户门户、客户数据隔离、外部账号体系，MVP 阶段是纯负担。
3. **数据敏感**。项目里含客户商业信息，少一个外部入口少一份泄露风险。

## 备选方案（为何没选）

- **B（轻参与）**：需要做只读门户 + 账号，工程量中等，但价值不明确——客户线上提的需求，最终还是内部人处理。
- **C（全参与）**：工程量最大，且"客户全程在线"不是团队的协作方式（他们靠线下/微信沟通）。

## 核心原则

**先解决内部痛点，不引入外部复杂度。** 如果未来客户确实需要线上参与，再以"轻参与"方式逐步加，不影响现有架构（角色体系已预留扩展空间）。

## 关联代码

- `backend/app/models.py` — `Role` 枚举只有 `admin/tech/instructor` 三种
- `backend/app/routers/*.py` — 所有接口用 `require_role` 限定内部角色
