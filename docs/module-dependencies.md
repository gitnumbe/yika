# 模块依赖图与影响分析（Impact Analysis）

> **目的**：开发某个功能模块前，先判断改动会波及哪些模块，防止"改一处、坏全局"。
> **使用方式**：改动前，在本文件找到要改的模块，看它的"改动影响面"，然后按下面的 checklist 逐条过一遍。

---

## 2. 影响等级分级

### 🔴 高影响（改动波及全局，必须全量回归）

| 模块 | 为什么高影响 | 改动的典型后果 |
|---|---|---|
| `models.py` | 所有 router/service 都依赖 ORM 模型和枚举 | 加/改字段 → 影响所有读写该表的接口 + 测试 |
| `schemas.py` | Pydantic 模型是接口契约 | 改字段 → 前端 api 调用 + 对应 router 全受影响 |
| `auth.py` | JWT + `require_role` 被所有 router 引用 | 改鉴权/权限 → 所有接口的访问控制受影响 |
| `config.py` | 所有模块读环境变量 | 改字段名 → 所有 `settings.xxx` 调用点失效 |
| `state_machine.py` | 需求状态机，业务核心规则 | 改状态/流转 → 需求流程 + 前端 Requirements 页 + 测试 |
| 前端 `api/client.ts` | 所有请求的封装 | 改 BASE/header → 所有页面请求失效 |
| 前端 `context/AuthContext.tsx` | 认证状态被所有页面用 | 改 token 逻辑 → 所有页面鉴权/跳转受影响 |

### 🟡 中影响（改动波及一组相关模块）

| 模块 | 影响面 |
|---|---|
| 某个 `services/*.py`（如 qa_service） | 影响依赖它的 router + 对应测试 |
| 某个 `routers/*.py`（如 requirements） | 影响对应的前端页面 + 该路由的测试 |

### 🟢 低影响（改动隔离，影响面小）

| 模块 | 影响面 |
|---|---|
| 单个 `pages/*.tsx` | 只影响该页面本身 |
| 新增独立的 service / router | 不影响现有模块（除非改了共享层） |

## 3. 影响分析 Checklist（改动前必答）

改动任何模块前，逐条回答：

1. **改哪个模块？** 它在依赖图的什么位置？（用上面的分级判断等级）
2. **谁依赖它？（下游）** 改它的接口/字段/行为，会连带影响谁？
3. **它依赖谁？（上游）** 它的依赖是否被我的改动连带修改？（如果是共享层，危险）
4. **改的是接口契约吗？** 函数签名、API 请求/响应、表结构、枚举值、状态流转——只要改契约，下游必受影响。
5. **有测试锁住行为吗？** 对应模块有没有测试？改动后跑哪些测试能确认没回归？
6. **回归范围是什么？** 列出必须跑的测试（🔴 全量，🟡 相关模块，🟢 仅本模块）。

## 4. 各模块"改动影响面"速查表

| 我要改 | 影响面 | 必须回归的测试 | 等级 |
|---|---|---|---|
| `models.py` | 所有 router + service + 前端 | `pytest tests/` 全量 + 前端 build | 🔴 |
| `schemas.py` | 对应 router + 前端 api 调用 | 相关 `test_*.py` + 前端 build | 🔴 |
| `auth.py` | 所有接口访问控制 | `test_auth.py` + 所有涉及 `require_role` 的测试 | 🔴 |
| `state_machine.py` | 需求流程 | `test_state_machine.py` + `test_requirements.py` | 🔴 |
| `config.py` | 所有读配置的模块 | 全量（启动即验证） | 🔴 |
| `services/qa_service.py` | `routers/qa.py` | `test_qa.py` | 🟡 |
| `services/llm.py` | 所有用 `get_llm`/`get_denoise_llm` 的服务 | `test_llm.py` + 相关 | 🟡 |
| `routers/requirements.py` | 前端 Requirements 页 | `test_requirements.py` | 🟡 |
| `pages/Requirements.tsx` | 仅该页面 | 前端 build | 🟢 |
| 新增 service/router | 无（除非动共享层） | 新增测试 + 全量 smoke | 🟢 |

## 5. 防止全局失控的三条硬规矩

1. **共享层改动必须全量回归**：`models.py`、`schemas.py`、`auth.py`、`config.py`、`state_machine.py`、前端 `client.ts`/`AuthContext.tsx` 是共享层，改完必跑全量测试 + 前端 build。
2. **契约先行**：改接口（函数签名、API 字段、表结构、枚举）前，先在本文档/决策文档里写清楚"契约怎么变"，再改代码，避免下游措手不及。
3. **测试是防回归的网**：每个模块改完，对应测试必须过；如果改动了契约导致下游测试失败，要么是设计问题（回去改设计），要么是契约真的变了（同步更新下游 + 测试），绝不能删测试掩盖。
